# Security

CampusLoop is a **zero-backend, zero-network** single-page app. The attack
surface is therefore the dependency tree, the static host, and the user's
own browser cache. This file is short on purpose — there is no service to
authenticate against, no API to rate-limit, no customer data to leak. The
"security" of CampusLoop is the security of the Web platform.

## Reporting

If you find a vulnerability in CampusLoop (including in a documentation
example that someone might copy), please email
**doge@tidalboundary.fun** rather than opening a public GitHub issue.
A reasonable disclosure timeline is 90 days.

## What is **not** in scope

- **The user's localStorage.** State at key `campusloop.v1` is owned by the
  user, on the user's disk. CampusLoop never reads from any other key, never
  writes to any other key, and never sends it off the device. Reviewers can
  reproduce this: open DevTools → Application → Local Storage and watch it
  during a full demo run.
- **The bundled dependencies.** `react` and `react-dom` are the only runtime
  dependencies (`package.json`), pinned to specific patch versions, audited
  by `npm install` against the registry on every clone. DevDependencies
  (`vite`, `typescript`, `vitest`, types) are never shipped to the user's
  browser.
- **The static host.** GitHub Pages is the documented distribution channel.
  GitHub Pages serves over HTTPS with HSTS preload and a content-security
  policy inherited from the GitHub CDN.

## What **is** in scope

| Surface | Risk | Mitigation |
|---|---|---|
| Cross-site scripting (XSS) via cover-uploaded image | A hostile cover render could embed a payload | Covers are **rasterised in-page** from style specs (no upload path, no remote fetch); the descriptor runs on the raw `ImageData`, never on user-supplied HTML |
| Prototype pollution | Could let a hostile caller mutate library state | `Object.freeze` on every shape in `src/lib/types.ts`; validation in `src/lib/store.tsx` rejects malformed localStorage payloads |
| Supply-chain | A compromised dependency could ship malicious code | Two-pronged: (a) `dependencies` contains only `react` + `react-dom`, (b) `npm run build` runs `tsc --noEmit` first so any change in the API contract is caught before the bundle is regenerated |
| Subresource integrity on third-party content | A hijacked CDN could ship a hostile font or image | The app **does not load any third-party resource at runtime** — no webfonts, no analytics, no telemetry, no remote imagery, no model files. The PageSpeed test on the live demo will show the only network calls are the static asset requests the user already made |

## Defence in depth

1. **HTTPS only.** The live demo and the GitHub Pages redirect are HTTPS.
2. **No remote code.** Every line of code that runs in the user's browser is
   in this repository, audited by the README's `npm run verify` step.
3. **No tokens.** There is no API key, no OAuth client, no session cookie to
   steal. The user cannot be impersonated because the user has no identity
   to lose.
4. **No input file handling.** Cover images are generated by the app's own
   rasteriser. There is no upload affordance, no `<input type="file">`, no
   drag-and-drop target.
5. **Audit-trail via tests.** The headline numbers in the README are emitted
   by the committed test suite, so a reviewer can run `npm run verify` to
   see exactly what is being claimed without trusting a manual hand-write.

## What we would add if there were a backend

A backend service would introduce authentication, secrets management, and
logging. Those are out of scope today; if they are ever introduced, this
file would grow to cover:

- Rate-limiting on the `/match` and `/forecast` endpoints (since they are
  the most expensive to recompute).
- API key scoping (read-only vs read-write).
- Per-tenant data isolation if multiple schools are onboarded.
- Audit logging of every match (which is today held only in localStorage).
